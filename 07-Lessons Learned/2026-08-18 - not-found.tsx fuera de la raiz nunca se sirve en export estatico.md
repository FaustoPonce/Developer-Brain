# `not-found.tsx` fuera de la raíz de `app/` nunca se sirve en `output: 'export'`

## Síntoma

Ninguno — no vino de un reporte. Surgió al preguntarme si el sitio tenía una 404
propia. La respuesta esperada era "sí" (el archivo existe, con contenido bilingüe
bien armado), pero al pegarle a una URL rota real, el HTML servido era el 404
genérico de Next ("This page could not be found"), no el propio.

## Impacto

Cero contexto, cero navegación de vuelta, marca ausente para el 100% de las URLs
rotas del sitio — probablemente desde el día uno del proyecto. El archivo llevaba
semanas en el repo, pasaba `npm run check` sin ninguna advertencia, y el ítem
"Página 404 propia" de la checklist de lanzamiento se podía marcar ✅ de buena fe
sin haber servido nunca el contenido real.

## Causa raíz

En un layout bilingüe con `[lang]/layout.tsx` como raíz efectiva (patrón ya
documentado en [[NextJS]], sección "Layout raíz con segmento dinámico"), el
`not-found.tsx` se había puesto en `src/app/[lang]/not-found.tsx` por analogía —
"vive al lado del layout que sí es la raíz real de la app". Anda perfecto en
`next dev`, porque ahí Next sí puede resolver el `notFound()` dentro del árbol de
rutas en tiempo de request.

Con `output: 'export'` no hay tiempo de request: `out/404.html` (lo que cualquier
hosting estático sirve para una URL sin archivo, incluida la config de Cloudflare
Workers Static Assets `not_found_handling: "404-page"`) sale **solo** de
`app/not-found.tsx` en la raíz literal de `app/`. Un `not-found.tsx` dentro de un
segmento dinámico nunca se compila a ese archivo — es una limitación conocida y
documentada de Next (confirmado por búsqueda, no solo por el repro propio), no un
bug puntual de este proyecto.

## Por qué no lo vi antes

`next dev` enmascara el problema por completo — ahí sí resuelve el `not-found.tsx`
anidado, así que probarlo en desarrollo da un falso positivo. Ningún chequeo
automático (`typecheck`/`lint`/`build`) puede detectarlo: el archivo compila bien,
está en el árbol de rutas, no hay ningún error. Solo se descubre pegándole a una
URL rota real contra el build exportado o el sitio en vivo y mirando el HTML
servido — el mismo patrón que [[2026-08-16 - Header compartido sin breakpoint
mobile pasa cualquier chequeo automatico]]: la falla vive en el layout renderizado,
no en nada que un compilador pueda verificar.

## Fix

Mover a `app/not-found.tsx` (raíz literal). Eso exige un `app/layout.tsx` (raíz)
mínimo — Next no permite un special file de raíz sin un layout de raíz que lo
envuelva. El riesgo obvio: si `[lang]/layout.tsx` ya renderiza su propio
`<html lang={locale}>`, ¿el layout raíz nuevo no duplica la etiqueta `<html>` en
todas las rutas reales? **Confirmado con un build real que no** — Next resuelve la
declaración `<html>` más profunda del árbol para cada ruta; el layout raíz nuevo
solo termina aplicándose a la página de 404 (la única que no tiene un `[lang]/layout.tsx`
por encima). El `lang` del layout raíz queda fijo en un idioma por defecto — no hay
forma de saberlo mejor para una URL que, por definición, no matcheó nada.

## Cómo lo prevengo

- Nuevo ítem en [[SEO Launch]]: la 404 propia se **verifica sirviéndola**, no se da
  por hecha porque el archivo existe. `curl` a una URL rota real (o al build
  exportado con un server estático local) y confirmar que el HTML devuelto es el
  propio, no el genérico de Next.
- En cualquier proyecto con `output: 'export'` + `[lang]/layout.tsx` como raíz
  efectiva: el único lugar válido para `not-found.tsx` es la raíz literal de `app/`,
  nunca dentro del segmento dinámico — sin importar qué tan natural se sienta
  ponerlo al lado del layout que sí es la raíz "real" del contenido.
